# Continuous integration

GitHub Actions runs `python3 scripts/check_project.py` on pushes, pull requests,
and manual requests. The check verifies that the main HISE project files are
present, parses the project settings, network XML, sample maps and user presets,
and checks the direct includes in the main interface script. It uses only the
Python standard library and can also be run locally from the repository root.

This is a repository integrity check, not a plugin build or a HISEScript syntax,
audio, or preset compatibility test. Hidden temporary files are excluded.
A passing result does not establish that the instrument can be exported or that
its presets sound and behave correctly.

## Before adding automated plugin builds

Establish and record a known-good local export first, including:

- The exact HISE source revision and any required modifications, SDKs, Faust
  version, compiler, and platform-specific settings.
- The intended export targets and the HISE project/preset used for the release.
  The project is at `Quetzalcoatl/Quetzalcoatl`; its main preset is
  `Presets/Quetzalcoatl.hip`.
- Confirm that the existing audio pool and generated non-audio pools work in
  exported plugins on both operating systems. CI must not regenerate the audio
  pool or require the original WAV files.
- Whether signing, notarisation and installers are required, and how secrets
  and release assets will be handled. Keep credentials out of the repository.
- A repeatable smoke test covering factory and existing user presets, sample
  and SFZ loading, and each supported plugin format and platform.

HISE documents its command-line export options at
<https://docs.hise.audio/glossary/command-line-tool.html>. Verify the commands
against the chosen HISE revision before adding a build job: options and
platform support can differ between versions. Keep release publication separate
from pull request checks until the build is reproducible.

## Installer requirements

Windows and macOS installers should include the plugin and application data:
`AudioResources.dat`, factory presets and wavetables. Merge the content into:

- macOS: `~/Library/Application Support/modularsamples/Quetzalcoatl`
- Windows: `C:\ProgramData\modularsamples\Quetzalcoatl`

For every supplied data file, install it if missing; replace an existing file
only when the supplied file has a strictly newer modification time. This includes
presets with matching paths. Preserve existing `GeneralSettings.xml` and
`User Presets/db.json` regardless of timestamp, to retain settings and favourites. Preserve destination files that are equal in age or
newer, and never remove unrelated files. Preserve source timestamps when
creating and extracting the content archive, and test comparisons and timestamp
resolution on both platforms. Same-name user edits can be replaced under this
rule if the supplied file is newer.

The `Verify release content` workflow can be run manually in GitHub Actions.
It downloads the [1.0.0 content archive](https://github.com/publicsamples/Quetzalcoatl/releases/download/1.0.0/Quetzalcoatl-content.zip)
and verifies the release asset SHA-256 pinned in `scripts/check_content.py`. It
also checks for unsafe paths and the presence of `AudioResources.dat`. It does
not build a plugin or an installer. If the content asset is intentionally
replaced, review the new archive and update the pinned checksum.

Windows builds are unsigned. macOS produces separate unsigned and signed
installers; the signed installer and its plugin binaries use Developer ID
identities and the installer is notarised and stapled.

The supplied 0.8.7 macOS expanded installer provides a reference: it contains
VST3 and Audio Unit components installed under `/Library/Audio/Plug-Ins`, and a
separate content component including presets, wavetables and
`AudioResources.dat`. Its postinstall script stages content under the system
Library and uses `rsync -u` to copy it into a user's Library. This is useful
historical context, not a verified implementation of the requirements above;
the replacement installer must be tested independently, including user and
home-directory selection and equal-timestamp cases.

## Local HISE baseline

The local project export examined on 10 November 2026 used the HISE fork
`RickTaylor79/HISE` at commit `a544b40ab0e67f6d1cf7e4b48ea10fdbebeb2b7b`
with JUCE submodule `b19c001a3553478723d8ed8e2fd74fd345c5154`. The HISE
checkout also had local generated Scriptnode database changes. This is an
observed baseline, not yet a verified clean CI toolchain. The project has
uncommitted changes, including the main HISE preset; a GitHub runner only sees
changes once they are committed and pushed.

CI builds the locally exported HISE project under `Binaries/` directly using
the pinned HISE and JUCE source; it does not compile or invoke HISE. The
exported `AutogeneratedProject.jucer` and `Source/` files must be committed
and refreshed whenever the HISE project changes. Build products and generated
`JuceLibraryCode/` are ignored. The supplied `AudioResources.dat` remains an
installer resource: plugin builds do not create or modify it and do not need
the original WAV files.

## Content archive inspection

The pinned ZIP has a `Quetzalcoatl/` root with `AudioResources.dat`,
`AudioFiles/*.hwt`, and `User Presets/`; it also includes `__MACOSX`,
`.DS_Store`, `GeneralSettings.xml`, and `User Presets/db.json`. Installer
packaging needs an explicit policy for metadata and user-specific settings.
The content archive does not include sample monoliths. CI separately downloads
[Samples.zip](https://github.com/publicsamples/Quetzalcoatl/releases/download/1.0.0/Samples.zip),
verifies its pinned SHA-256, and includes its `.ch1` files in each package.

The ZIP's audio pool is byte-for-byte identical to the local `PooledResources`
audio pool. The other resource pools are generated from the tracked project
assets during export. A full hosted build and runtime test are still required.

The Windows Inno Setup package and macOS packages use the content merge helpers
under `installers/`. Linux ships a VST3, content, an install script and
instructions. The merge helpers can be checked with `tests/test_macos_merge.sh`,
`tests/test_windows_merge.ps1` and `tests/test_linux_install.py`. The packages
still need clean-install and upgrade tests on their target operating systems.

The staging tool `scripts/stage_content.py` verifies the pinned content ZIP,
removes macOS archive metadata, checks Windows name collisions and requires
UTC timestamps from ZIP metadata. It produces a clean directory that can be
passed to the platform merge helpers. The manually triggered content workflow
also exercises staging.

The manually triggered `Experimental HISE plugin builds` workflow prepares
the saved Projucer project for the runner and builds macOS AU/VST3 and Windows
VST3 against the pinned HISE source. It has not yet been verified on hosted
runners. It builds Windows and macOS installers and a Linux ZIP as short-lived
artifacts; it does not publish releases. The macOS workflow signs the plugin
binaries in one package and leaves the other unsigned. Regenerate and commit the HISE
export after project changes so the embedded preset and scripts are current.

macOS AU and VST3 builds must be universal (`arm64` and `x86_64`). The
workflow requests both architectures and uses `lipo` to reject missing or
single-architecture plugin binaries before uploading artifacts.

The manual macOS build can reuse an Xcode build cache after a successful
architecture check. Its exact key includes the toolchain and runner image,
pinned HISE revision, export source, DSP source and workflow configuration.
There are no fallback keys. Select `clean_build` to bypass the cache when
checking a release or investigating a suspect incremental build. Cache hits
do not guarantee a speedup: Xcode can rebuild files when runner timestamps
change. Compare restored-build timing against a clean build before relying
on the cache.

## Package and signing status

The signed macOS package contains Developer ID Application-signed AU and VST3
binaries and is signed with a Developer ID Installer identity, submitted to
Apple for notarisation, and stapled after acceptance. The other package is
unsigned and unnotarised. The workflow expects these organisation secrets:

- `DEVELOPER_ID_APP_CERT_P12_BASE64` and `DEVELOPER_ID_APP_CERT_PASSWORD`
- `DEVELOPER_ID_INSTALLER_CERT_P12_BASE64` and
  `DEVELOPER_ID_INSTALLER_CERT_PASSWORD`
- `APPLE_ID`, `APPLE_TEAM_ID`, and `APPLE_APP_SPECIFIC_PASSWORD`
- Optional `DEVELOPER_ID_APPLICATION_IDENTITY`

The unsigned package is uploaded before the signing steps, so it remains
available if signing or notarisation fails. Verify the signed package with
`pkgutil --check-signature` and `xcrun stapler validate`, then perform
clean-install and upgrade tests on a separate macOS system before release.

The Windows installer installs the VST3 in the common VST3 folder and merges
content into ProgramData. It grants ordinary users modify access to the shared
application-data folder so presets and favourites remain writable. CI sets HISE's system application data option for the
Windows plugin; macOS and Linux use user application data. Linux uses
`~/.config` and `~/.vst3` (matching this HISE/JUCE build).

## Sample location and links

All packages install or merge the sample monoliths under the installing user's
Music folder, in `modularsamples/Quetzalcoatl/Samples`. Existing sample files
are replaced only when the package version is newer. The installers write the
absolute sample path to `LinkOSX`, `LinkWindows`, or `LinkLinux` in the HISE
application-data directory. They intentionally update an existing link to
point to the newly installed library. Windows runs the merge as the original
installing user so redirected Music folders and alternate administrator
credentials resolve correctly. The Windows application-data folder and its
link are shared across users, so a later install by another user will update
the link for all users. macOS uses the logged-in console user's home; Linux
uses the Music directory in `~/.config/user-dirs.dirs` when available.

The content ZIP and sample ZIP are both pinned and checksum-verified. Test
first installs and upgrades on Windows, macOS and Linux before release,
including non-ASCII paths and existing sample libraries.
